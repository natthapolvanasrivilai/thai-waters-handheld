# Pocket Reel revision constitution

This is the release decision record, not an assertion that the current device is ready. Continue ordinary development commits, reviewed PRs, non-promotional engineering checkpoints and existing read-only verification without a production gate. Follow existing owner-private distribution restrictions and the hardware holds. In particular, this policy does not turn a public repository, public CI log, nightly artifact or GitHub prerelease into authorization to disclose private source, hardware, evidence or manufacturing data.

| State | Gate |
|---|---|
| Engineering checkpoint | Clearly mark what changed, exact source, unresolved safety and test gaps. No ready-for-use, production or order claims. Existing build/verification continues; the nightly package remains a CI checkpoint, not a GitHub release. |
| Deliberate prototype promotion | Pass the appropriate minimum in each included discipline and the non-waivable hazard review. Inert prints also require native printability. Powered prototypes require PCB layout/populated fit, controlled bench limits, measured protective/fault behavior, and fit/service first article. Failure blocks the revision; optional incomplete checks remain pending, not N/A. |
| Production promotion or any production order | All checks pass, full powered product scope, repository verified private, express owner approval in a GitHub review tied to the exact evidence commit and source. Recheck current facts at action time; no purchase or public distribution is implied. |

**Every intended release tag must first pass the read-only pre-tag gate. Every promoted prototype and production release must include the offline handbook HTML as an uploaded release asset.** Engineering checkpoints and non-release build artifacts are not promotions. The snapshot is standalone and embeds the exact source text, release version/tag, product, hardware, firmware and software revision identifiers (or an explained N/A for an absent discipline), exact source commit, what changed, and all evidence statuses. The current handbook design/deployment is separate.

A software-only prototype cannot contain hardware outputs. Explain why omitted hardware checks do not apply. An inert prototype cannot energize any circuit; it may mark measured active power protection N/A with a rationale, but it cannot omit hazard review. Only designated check IDs allow N/A; production does not. Keep safety limits appropriate to the test, and retain independent human review even when the script passes.

## Minimum evidence and production closeout

- **Mechanical/FDM:** exact CAD, native print project/configuration and material; check overhang supports and removal, weak/thin features, visible surface defects, dimensional/first-article evidence.
- **PCB:** schematic, ERC, exact BOM and footprint provenance; layout DRC, electrical/mechanical keepouts, placements and 3D assembly; physical bring-up with calibrated observations. Identify unresolved component/connector substitutions by exact identity.
- **Power:** written hazards, sources/load and foreseeable misuse, explicit permitted exposure; bench controls, current, charging, temperature and isolation limits; measured fault protection with limits, setup, time, readings and disposition. Record applicable product safety/compliance evidence before full production.
- **Software/firmware:** build source/digests; hardware compatibility, backed-up saves and recovery; target regression, migration, update and rollback; representative end-to-end endurance with the real build.
- **Assembly:** version-matched interfaces, tool access, service instructions and datum sequence; no-force physical fit and repeatable acceptance/QC; evidence for all released accessories.
- **Packaging:** exact configuration, BOM, serial/lot traceability; protection, labels, instructions and compliance; validation for intended transportation/load/region.

## Per-revision workflow

1. Lock the exact source commit (assembly and part revisions, PCB/BOM, firmware and native slices). Copy [the blank manifest](template.json) to a revision-specific filename in this directory. A separate evidence commit follows the source commit. Do not fabricate evidence or record only its intended path.
2. For each check, capture method, acceptance limit, observed result, artifact checksum, date and reviewer in tracked files under `verification/revision-evidence/`. In public prototype scope include only explicitly shareable evidence. A human must determine whether evidence is sufficient; the validator enforces structure and digests, not factual accuracy.
3. Use the local renderer and policy unit tests for preflight. A local fixture or locally supplied facts file does not convey authorization or prove a live draft includes the release asset.
4. For both release stages, build the snapshot only from the exact source Git object via `python3 tools/release_handbook.py . quality/revision-gates/<revision>.json <output.html>`. Use the canonical name `Pocket-Reel-Handbook-<version>-<revision>.html`, record its SHA-256 in the manifest, and track the snapshot at `verification/revision-evidence/handbooks/<name>`. The gate independently rerenders and compares bytes, so older HTML does not pass even if a stale checksum was recopied. Do not expose the owner-private wiki or its derived snapshot through a public repository/release. A public prototype requires a deliberately authorized, curated edition tracked under `docs/release-handbook-public/` in the exact source (must include Home.md); otherwise stop rather than substituting or publishing private files. Public builds reject exact copies of private Markdown chapters and direct private-wiki links; that is not DLP and does not replace human confidential-content review of the curated source.
5. Production only: the owner reviews the evidence PR at its **current exact HEAD**; the approving review must include a standalone line `release-gate: production REVISION FULL_SOURCE_SHA`. Use a reviewable PR author distinct from the owner so GitHub allows the owner to approve it. A newer owner rejection/dismissal, changed head, missing approval or public repository fails both gates. Revise and re-review when evidence or source changes.
6. **Before any tag creation**, from the trusted default branch manually dispatch **Revision release gate** with phase `pre-tag`, the intended tag, intended source SHA, evidence SHA, tracked manifest path and production review PR if applicable. Leave release ID and asset name empty. The gate validates exact reviewed evidence and the prospective offline snapshot, then requires that the exact GitHub tag ref be confirmed missing and no tag by that name exist in the checkout. An unexpected GitHub error or an existing tag with even the same target fails. Verify the successful `check_revision` job and the reported tag/source/evidence tuple. A pass grants no new permission and does not reserve a tag: recheck absence, authority and the same tuple when creating it; never move or overwrite an existing release tag.
7. Only an authorized releaser may then create the approved tag on the exact source and stage a draft GitHub release with the matching HTML asset.
8. From the same trusted branch, dispatch phase `pre-publish` for the **same** tag/source/evidence tuple, adding the draft release ID and exact staged handbook filename. This independent phase rechecks evidence and owner review, resolves the actual tag Git object (including annotated tags), and downloads and hashes the uploaded draft asset. A missing draft asset, tag on the wrong source, or release-stage mismatch fails. Verify a successful `check_revision` job again, not merely policy unit tests.
9. A passing check permits a human to consider promotion. Before promotion/order use the latest result, verify privacy, review, tag and staged asset have not changed, and obtain separate authority for the action as required. Record exact source, evidence run/commit, approved artifact SHA-256 and production lot/order in a controlled record.

## Technical boundary

The proposed gate does not publish, sign, power, merge, tag, pay, change visibility or create an order. Verified nightly build/package artifacts are retained; automatic nightly GitHub prerelease publication is disabled to avoid a handbook-free release. The old nightly publisher refuses publication before it reaches GitHub; it can be reintroduced only through the same live handbook gate. A repository administrator must adopt it in rulesets/required checks and integrate it into any future production-publish or ordering workflow; manual tagging (including the possibility someone creates a tag after preflight), direct GitHub releases, alternate workflows and external orders are not technically prevented by this repo-only proposal. Configure repository-admin tag creation/update rules and restrict publishing credentials to a trusted promotion flow to make the pre-tag/pre-publish sequence enforceable. GitHub Actions settings/ruleset protection and private visibility must be verified independently before use. The owner’s public engineering/development checkpoint authority is not extended.
